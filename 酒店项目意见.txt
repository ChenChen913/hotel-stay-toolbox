# 二、规则引擎这一层，我认为是目前项目最有价值的部分

你现在已经把：

> 用户回答 → 条件 → 物品 → 数量

抽成了独立规则。

比如：

```ts
when: c => c.prefs.sleep
```

决定是否出现眼罩、耳塞。

再比如：

```ts
qty: c => c.adults * (c.nights + 1)
```

决定消耗品数量。

而且 `buildPrep()` 是独立的纯函数：

```text
Conditions
    ↓
buildPrep()
    ↓
PrepItem[]
```

这很好。

因为以后你要改规则，不需要把 Vue 页面逻辑和规则搅在一起。

**如果把它作为你的作品集项目，我反而会重点展示这一层。**

# 十二、我建议下一版正式加入 `Guest`

例如：

```ts
interface Guest {
  id: string;
  type: 'adult' | 'child' | 'elderly';
  gender?: 'male' | 'female' | 'private';
  childAge?: ChildAge;
  role?: 'self' | 'partner' | 'family' | 'friend' | 'colleague' | 'other';
}
```

然后：

```ts
interface Stay {
  ...
  guests: Guest[];
  ...
}
```

这样：

```text
入住人
├── 我
│   └── 男
│
├── 伴侣
│   └── 女
│
└── 儿童
    └── 5岁
```

才真正成立。

# 十四、还有一个我认为现在必须重新考虑的问题：数量公式

你现在 README 写：

> 消耗品按「人数 ×（晚数 + 1）」计算。([GitHub][1])

代码也是这么干的。

这个作为 V1 的**默认估算公式**可以。

但不要把它变成系统的“真理”。

比如：

### 一次性马桶垫

2 人 × 3 晚 + 1：

> 8片

这个可以理解。

但是：

### 一次性床单

2 人 × 3 晚 + 1：

> 8套

这就明显不是所有人的使用方式。

### 湿巾

2个人 × 4晚：

> 到底应该几包？

没办法用人数简单推导。

所以以后应该从：

> `qty = 公式`

升级成：

> **默认数量规则 + 用户可调整**

你现在实际上已经支持手动修改，因此这个问题不严重。

但文档里最好明确：

> **“系统数量是建议值，不是标准答案。”**

# 十五、还有一个我觉得很明显的产品问题：你的“好物”目前更像收藏夹，还不是“采购系统”

现在 `GearView` / `GearPanel` 主要做的是：

> 某个物品 → 看你的品牌收藏。

而我们之前讨论的真正链路是：

```text
我需要这个东西
       ↓
系统推荐
       ↓
我决定买
       ↓
加入购买清单
       ↓
购买
       ↓
已买
       ↓
加入本次入住
```

你现在还没有完整做到这一层。

目前更多是：

> **“我对这个物品有什么好物收藏？”**

这没错。

但下一阶段可以变成：

### 🛒 采购状态

```text
眼罩
数量：1
状态：待购买

[查看我的推荐]

○ 未购买
○ 已购买
○ 家里已有
```

这样“好物”和“入住准备”才真正形成闭环。

# 十六、还有一个很小但很实际的问题

你现在问卷有：

> 1人 / 2人 / 3人及以上

但实际上 `adults` 是：

```ts
1 / 2 / 3
```

也就是说：

> **“3人及以上”实际上被压缩成了 3 个成人。**

这会直接导致数量错误。

比如：

> 4个成年人入住

系统还是：

> 成人数 = 3

那么：

> 牙刷 = 3

这显然不对。

### 这个我建议马上修。

不要用：

> 1 / 2 / 3+

作为内部数据。

UI 可以：

> 1人 / 2人 / 3人 / 4人 / 5人……

或者：

> 3人及以上 → 出现数字输入器

内部必须保存真实人数。

# 十七、还有一个值得注意的问题：儿童目前只有一个年龄段

现在：

```ts
childAge
```

是整个入住的儿童统一年龄。

那么如果：

> 两个孩子

一个：

> 2岁

另一个：

> 8岁

系统没办法表达。

这就是同一个问题：

> **人员信息被“数量 + 一个属性”压扁了。**

所以如果你准备正式升级数据模型，我建议：

> **不要再继续给 `Conditions` 打补丁。**

直接进入：

### `Guests[]`

# 二十、所以我现在不建议你继续“加功能”

这是我看完代码后最想说的一句话：

> **现在不要再让 AI 往里面塞新的物品、新的知识、新的页面。**

你现在已经到了一个非常典型的：

> **V1 数据模型校正期。**

最值得做的下一步只有一个：

## 把 `Conditions` 升级成真正的「入住人模型」。

也就是：

```text
Stay
│
├── Guests[]
│     ├── Guest 1
│     ├── Guest 2
│     ├── Child 1
│     └── ...
│
├── Conditions
│     ├── date
│     ├── nights
│     ├── purpose
│     └── prefs
│
├── PrepItems[]
│     ├── 使用谁
│     ├── 数量
│     ├── 家里带/购买
│     └── 是否完成
│
├── Checkin
│
└── Checkout
```

然后再解决：

**真实人数 → 每个人 → 物品使用人 → 数量 → 采购状态**

这一整条链。

一旦这条链通了，你现在这个项目就从：

> **“一个做得不错的酒店 Checklist”**

真正变成：

> **“围绕一次入住建立个人准备计划的工具。”**

而且我觉得这也是你现在最值得继续打磨的地方。

另外，仓库目前已经有 **29 次 commit、GitHub Pages、Vitest、GitHub Actions、备份/恢复、本地存储和 PWA**，工程基础其实已经够 V1 了；现在最大的价值不是继续堆技术，而是把**产品数据模型**再打磨一轮。([GitHub][1])

如果按我现在看到的代码继续开发，我会把下一阶段直接定成 **V1.1：入住人模型 + 采购状态 + 真正的多人清单**，暂时不碰 AI。
