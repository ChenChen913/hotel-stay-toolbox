# 未来功能规划（V1.2 / V2 候选）

> 本文件记录**已讨论过、但当前 V1 明确不实现**的功能。来源：聊天记录定稿、《酒店项目意见.txt》外部评审、代码中已出现的扩展位。
> 原则：**高频场景优先，低频复杂场景文档化，真正有需求时再实现。**
> 当前 V1 主用户 = 项目作者本人，以 1 人入住为主，偶尔 2 人。

---

## 1. 完整 Guest 入住人模型（V1.2 首选）

- **为什么未来可能需要**：多人入住时「入住人1」没有真实身份，物品使用人绑定只是 UI 占位；性别、关系等字段未来可能影响推荐（如女士→防身用品提示）。
- **为什么暂不实现**：当前主用户是 1 人入住，多人是低频场景；完整模型需要重做向导交互（谁是谁、关系、隐私），成本高且会拖慢高频流程。
- **未来怎么实现**：`Stay.guests: Guest[]`（id/kind/gender/role/childAge），`PrepItem.assigneeIds: string[]` 引用 Guest id；向导第 2/3 步生成 Guest 实体，物品行下拉改用 guest id。
- **已预留的兼容性**：`Stay.guests` 字段已存在（轻量版，label 稳定）；`PrepItem.assign` 存 label 字符串，升级为 id 引用时只需一次映射迁移。
- **重新考虑的时机**：真实出现 3 人以上、多儿童、需要按人分摊物品的行程时。

## 2. 采购状态闭环（待购买 → 已购买 → 家里已有）

- **为什么未来可能需要**：外部评审 §15 指出「好物」目前是收藏夹不是采购系统；「建议购买」的物品没有购买状态，无法形成 需求→购买→入库→备齐 的闭环。
- **为什么暂不实现**：单人高频场景下，勾选「已备齐」已覆盖主要需求；购买状态会为每行增加一层交互。
- **未来怎么实现**：`PrepItem.purchase?: 'todo' | 'bought' | 'home'`；对「建议购买/到店购买」物品显示三态切换；好物页可「加入本次入住」。
- **已预留的兼容性**：`PrepItem` 为接口，新增可选字段不影响旧数据；`done`（已备齐）语义不变；好物已是「物品名称 + 品牌」条目（v5），与清单物品名称同源，接「加入本次入住」时可直接改写成 `PrepItem`。
- **重新考虑的时机**：真实使用中频繁出现「买没买忘记录」的情况时。

## 3. 多儿童独立年龄

- **为什么未来可能需要**：两个儿童（如 2 岁与 8 岁）需要的物品完全不同，当前单一 `childAge` 无法表达。
- **为什么暂不实现**：多儿童是低频场景；Guest 完整模型（§1）天然解决此问题（每个儿童一个 Guest 实体），不应单独打补丁。
- **未来怎么实现**：并入 §1 Guest 模型，每个 child Guest 独立 `childAge`，物品按 Guest 生成。
- **已预留的兼容性**：`Guest.kind: 'child'` + `childAge` 字段已在类型中定义。
- **重新考虑的时机**：与 §1 一并做（V1.2）。

## 4. 性别 / 关系规则

- **为什么未来可能需要**：部分物品有性别倾向（剃须刀/卸妆棉），关系影响场景（情侣→浴缸套）。
- **为什么暂不实现**：聊03 定稿原则——「性别、关系不触发物品，避免刻板推荐」；当前用「可选物品 + 自定义添加」覆盖，无规则损失。
- **未来怎么实现**：Guest 性别/角色字段已预留；规则表新增 `when: g => g.gender === 'female'` 类条件，仅在证据充分时启用（如卸妆棉→女士）。
- **已预留的兼容性**：`Guest.gender/role` 可选字段已定义。
- **重新考虑的时机**：真实多人使用反馈出现明确的性别/关系需求时。

## 5. PC 宽屏双栏布局

- **为什么未来可能需要**：外部评审 §18 指出当前是「移动端居中放大」，PC 未做双端设计。
- **为什么暂不实现**：作者自述主要在手机上使用；`max-width: 680px` 居中在 PC 可用。
- **未来怎么实现**：`@media (min-width: 1024px)` 下清单左栏 + 详情右栏；仅 CSS，无结构改动。
- **已预留的兼容性**：样式全部集中在 global.css 与组件 scoped style，无内联宽度。
- **重新考虑的时机**：PC 端使用时长超过阈值或需要演示作品集时。

## 6. AI 能力（智能推荐 / 行程对话）

- **为什么未来可能需要**：未知场景下推荐物品（如「去三亚开会带什么」）。
- **为什么暂不实现**：项目核心价值是**规则可解释**；AI 是聊03 定稿的「独立入口、可选能力」，规则引擎已覆盖高频场景。
- **未来怎么实现**：独立入口调用 LLM，把 `Conditions` + 现有清单作为上下文，输出为「自定义物品建议」，用户确认后进入清单。
- **已预留的兼容性**：清单与条件均为结构化数据，可直接序列化为 prompt。
- **重新考虑的时机**：规则覆盖遇到瓶颈（用户频繁手动添加同类物品）时。

## 7. 法规条目到期复核提醒 UI

- **为什么未来可能需要**：知识库时效性条目（治安法 2026 新条号、12301 已取消、调解期限 60 自然日）已带 `reviewBy` 字段，法规更新后需要复核。
- **为什么暂不实现**：字段已存在，当前条目均未到期；提醒 UI 是小事。
- **未来怎么实现**：`KnowledgeView` 顶部在 `reviewBy` 过期时显示「以下条目需要复核」横幅。
- **已预留的兼容性**：`KnowledgeEntry.reviewBy` 字段已定义并有测试。
- **重新考虑的时机**：第一批 `reviewBy` 到期时（2027-03）。

## 8. 季节 / 目的地天气自动推断

- **为什么未来可能需要**：冬装、驱蚊等物品与季节强相关，自动推断可少问一个问题。
- **为什么暂不实现**：需要接入天气/地理位置服务（外部依赖），与「无后端、无外部服务」原则冲突；当前用「蚊虫季节」开关代替。
- **未来怎么实现**：向导第 1 步选目的地城市后，按历史气候表（本地静态数据）推断季节，预填开关。
- **已预留的兼容性**：`prefs.mosquito` 等开关即推断结果的落点。
- **重新考虑的时机**：接入任何外部服务（打破无后端原则）时一并考虑。

## 9. 好物 → 清单的双向关联

- **为什么未来可能需要**：现在好物是「物品名称 + 品牌」的独立收藏，「好物」页新增的物品不会自动进入本次清单；用户加了一件清单里没有的东西，还得回行程页再手输一遍。
- **为什么暂不实现**：当前好物条目已带 `name`/`cat`，与清单物品名称同源，真要接的时候成本很低；先看真实使用中是否会频繁手动同步。
- **未来怎么实现**：好物行加「加入本次行程」按钮，按 `cat` 落到清单分类，`source` 标为「自定义」；反向在清单里给自定义物品补「记入好物」。
- **已预留的兼容性**：`GearEntry.name/cat` 与 `PrepItem.name/cat` 字段一致，`PrepItem.source` 已有 `'自定义'` 取值，无需改存储结构。
- **重新考虑的时机**：出现「好物页加过、清单里又手输一遍」的重复操作时。

## 10. 好物字段扩展（使用体验/回购意愿）

- **为什么未来可能需要**：现在只记「名称 + 品牌」，记不下「为什么好」和「还会不会再买」。
- **为什么暂不实现**：V1 主用户是作者本人，名称 + 品牌已够用；多字段会让添加流程变长，拖慢高频操作。
- **未来怎么实现**：`GearEntry` 增加可选 `note?: string`（一句话体验）与 `repurchase?: 'yes' | 'no' | 'maybe'`；展示仍以「名称 + 品牌」为主行，备注降级为次行。
- **已预留的兼容性**：`GearEntry` 是接口，新增可选字段不影响已存 v5 数据；`gearList()` 读入时不会因为缺字段报错。
- **重新考虑的时机**：收藏条目多到「想不起来当初为什么记它」时。

## 已明确的「不做」

| 事项 | 理由 |
|---|---|
| 女士「门口放男士拖鞋」等伪装策略 | 外部核查 D7：效果未经证实，属个人策略 |
| 便携除螨仪、医用毛刷刷床单 | 外部核查 E11/E12：对虫害无效 |
| 「湿毛巾防毒」类消防表述 | 官方已修正：及时撤离方为上策 |
| 市售防偷拍检测仪推荐 | 公安部通报为伪劣产品（知识库 k3/k4 已覆盖警示） |
| 多人权限 / 账号系统 | 单人本地工具，与「无后端」原则冲突 |
